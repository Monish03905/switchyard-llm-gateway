# Deployment

Three ways to run the yard, cheapest first. All of them work with **no provider
key**: the simulator takes over and every number on screen is labelled simulated.

## 1. Local, zero setup

```bash
python -m venv .venv
# Windows
.venv\Scripts\activate
# macOS / Linux
source .venv/bin/activate

pip install -r requirements-dev.txt
cp .env.example .env          # optional; defaults work with no keys
uvicorn app.main:app --reload
```

Open http://127.0.0.1:8000 — FastAPI serves the built cockpit if `web/dist`
exists, otherwise the API root tells you how to build it. OpenAPI lives at
`/docs`, health at `/health`, Prometheus text at `/metrics/prometheus`.

Frontend development with hot reload:

```bash
cd web
npm ci
npm run dev        # http://localhost:5173, proxies /api, /v1, /health to :8000
npm run build      # writes web/dist, which FastAPI serves at /
```

Tests and the CI gate:

```bash
pytest -q
python scripts/policy_gate.py
```

## 2. Docker

```bash
docker build -t switchyard .
docker run --rm -p 8000:8000 --env-file .env \
  -v switchyard-data:/data switchyard
```

The image is multi-stage: Node builds the cockpit, then a Python slim image
copies only `app/`, `scripts/`, and `web/dist`. It runs as a non-root user with a
healthcheck and defaults to SQLite under `/data`. Drop `--env-file` if you have no
`.env`; the container still boots in simulator mode.

## 3. Compose with Postgres and Redis

```bash
cp .env.example .env     # optional; compose reads it when present
docker compose up --build
```

What you get:

* `yard` on http://localhost:8000, healthchecked, restarts on failure.
* `postgres:16` with a named volume and `pg_isready` gate; the app uses
  `postgresql+asyncpg` and creates tables on boot.
* `redis:7` with a 128 MB LRU cap; the response cache switches to Redis
  automatically (`/api/overview` → `guardrails.cache.note` confirms it).

The app still runs **one uvicorn worker on purpose** — cache, breaker, limiter,
and chaos state are in-process. See "Scaling" below before raising that.

## 4. Render (hosted)

1. Push this repository to GitHub.
2. Render → **New → Blueprint** → choose this repository. Render reads
   `render.yaml` from the repository root.
3. On the Starter plan (required for a persistent disk), Render builds the
   Dockerfile, mounts a 1 GB disk at `/data`, and healthchecks `/health`.
4. In the dashboard, fill the `sync:false` secrets: `GATEWAY_API_KEY`,
   `ADMIN_TOKEN`, and optionally `GROQ_API_KEY` / `OPENAI_API_KEY`.
   `LEDGER_KEY` is generated by Render and kept stable across deploys.

When it is live, add the URL near the top of the README and record a fresh
gauntlet run so the hosted numbers are your own.

Any Docker host works the same way (Fly.io, Railway, ECS). The only hard
requirements are a writable path for SQLite (or a Postgres URL), port `8000`
(or `PORT`), and `/health` for the probe.

## 5. Going live with a real provider

1. Put `GROQ_API_KEY=...` (or `OPENAI_API_KEY=...`) in `.env`. Never commit it;
   `.env` is gitignored, and `.env.example` contains only placeholders.
2. Keep `PROVIDER_MODE=auto` (use a key if present) or set `live`.
3. Restart. `/api/overview` → `meta.mode` becomes `live`, and the simulator note
   disappears from the cockpit.
4. Pin models with `GROQ_MODEL_CHEAP`, `GROQ_MODEL_STRONG` (and the OpenAI
   equivalents). Prices live in `app/gateway/cost.py`; update that sheet when a
   vendor changes pricing, or the savings story becomes fiction.
5. Run the gauntlet once from the cockpit. Treat the first live batch as a smoke
   test: if the pass-rate gap between thrift and prime is tiny, your tasks are
   too easy to justify a router.

## 6. Configuration that matters

| Variable | Default | Notes |
|---|---|---|
| `PROVIDER_MODE` | `auto` | `auto` / `live` / `simulated` |
| `DATABASE_URL` | `sqlite+aiosqlite:///./switchyard.db` | Postgres: `postgresql+asyncpg://...` |
| `REDIS_URL` | empty | empty → in-process LRU cache |
| `DAILY_BUDGET_USD` | `5` | `0` disables the guard |
| `RATE_LIMIT_RPM` | `120` | `0` disables limiting |
| `GATEWAY_API_KEY` | empty | empty → open gateway, identity by IP |
| `ADMIN_TOKEN` | empty | empty → admin levers open (demo only) |
| `STORE_PROMPTS` | `false` | opt-in full prompt storage |
| `LEDGER_KEY` | dev placeholder | generate a real one in production |
| `CACHE_TTL_S` | `3600` | exact-match cache lifetime |
| `MAX_RETRIES` | `2` | per candidate |
| `BREAKER_*` | `3 / 60s / 20s` | threshold / window / cooldown |

Full list with comments: [`.env.example`](../.env.example).

## 7. Scaling honestly

The current design is a **single-instance appliance**, and that is fine for the
job it does (a portfolio-grade gateway with an audit trail). To scale out:

1. Move the response cache to Redis (`REDIS_URL` already does this).
2. Replace `LedgerLock` with a Postgres advisory lock so chain appends serialize
   across processes.
3. Move rate limiting and chaos arming to shared storage, or accept per-instance
   limits.
4. Move gauntlet execution to a worker/queue. Today batches run as in-process
   background tasks, which are lost on restart; the startup hook marks them
   cancelled with a reason instead of leaving zombies.

Until then, run exactly one replica. Multiple workers would produce duplicate
sequence chains and inconsistent budget views.

## 8. Operations runbook

```bash
# Is the ledger intact?
curl -s localhost:8000/api/ledger/verify

# Arm three simulated failures, then send a request to watch retry + fallback
curl -s -X POST localhost:8000/api/admin/squall \
  -H 'content-type: application/json' -H 'X-Admin-Token: ...' \
  -d '{"fails": 3}'

# Disarm, purge cache, reset breakers
curl -s -X DELETE localhost:8000/api/admin/squall -H 'X-Admin-Token: ...'
curl -s -X POST localhost:8000/api/admin/cache/purge -H 'X-Admin-Token: ...'
curl -s -X POST localhost:8000/api/admin/breakers/reset -H 'X-Admin-Token: ...'
```

* **Backups**: copy the SQLite file (with WAL checkpointed) or `pg_dump`; the
  ledger CSV export is a portable second copy.
* **Rotating `LEDGER_KEY`** intentionally breaks verification of old receipts.
  Export first, then rotate, then start a fresh chain and say so in the release
  notes. Never silently rotate.
* **Budget**: `DAILY_BUDGET_USD` is read per request; changing it needs a restart
  because settings are loaded at startup.
* **429s**: raise `RATE_LIMIT_RPM` or put the app behind a proxy that forwards
  `X-Forwarded-For` (used for the hashed client identity).

## 9. CI

`.github/workflows/ci.yml` runs three jobs on every push and PR:

1. **verify** — `ruff check`, `ruff format --check`, `pytest`, then `npm ci` and
   `npm run build`.
2. **eval-gate** — `python scripts/policy_gate.py`, a 36-task × 3-policy
   simulated gauntlet. It fails if prime < 95%, router < 90%, or the router saves
   less than 10% versus prime. The summary is written to the GitHub Actions job
   page, so the cost/pass-rate story is attached to every commit.
3. **docker** — builds the shipping image, boots it, and polls `/health` until
   the container reports healthy. A deploy that cannot start is caught in CI.

The gate needs no secrets and no network. That is deliberate: a test that depends
on a provider is a demo, not a gate.
